1. EL BLOQUEO DE NAMESPACE, CONFIRMADO POR UNA SEGUNDA VIA INDEPENDIENTE
========================================================================
La pasada anterior probo el bloqueo creando el campo por la UI de Setup. Esta vez se probo por
el camino distinto del Metadata API, que es el que usaria un despliegue automatizado:

    despliegue de CustomField con <fullName>Engagement_Level__c</fullName>
      resultado del deploy   componentSuccesses: Contact.Engagement_Level__c  created: true
      parecia sin prefijo

    pero el metadato realmente almacenado, consultado por Tooling API:
      SELECT DeveloperName, NamespacePrefix FROM CustomField WHERE Id = '00NRt00001KhpvgMAB'
        DeveloperName   : Engagement_Level
        NamespacePrefix : Auctifera          <-- la org lo prefijo igual

    y la consulta literal del codigo, ejecutada contra esa org:
      SELECT Id, Engagement_Level__c FROM Contact WHERE Email = '...' LIMIT 2
        -> INVALID_FIELD: No such column 'Engagement_Level__c' on entity 'Contact'

  CONCLUSION: el prefijo no es un artefacto de la UI. El `fullName` que devuelve el deploy es el
  nombre de ORIGEN, no el almacenado. Cualquier automatizacion que confie en ese acuse creeria
  haber creado el campo sin prefijo. Dato util para el equipo.

  Una restriccion adicional encontrada en estas orgs: no permiten crear Connected Apps
  ("You can't create a connected app. To enable connected app creation, contact Salesforce
  Customer Support"), y no hay permiso de usuario que lo habilite. El flujo JWT no es montable
  ahi. Eso afecta SOLO la obtencion del token, que no forma parte de ningun AC.

5. EDGE CASE — EL ESCAPE DE SOQL, PROBADO CONTRA EL PARSER REAL
================================================================
El test del dev verifica la forma de la cadena contra un fetch simulado. Aqui se ejecuto contra
el parser real de Salesforce, comparando con y sin escape:

  entrada                          sin escapeSoqlLiteral        con escapeSoqlLiteral
  -------------------------------  ---------------------------  ---------------------------
  qa-tc-163-o'hara@example.com     MALFORMED_QUERY              ejecuta, 1 fila
                                   "unexpected token: '@'"
  back\slash@example.com           MALFORMED_QUERY              ejecuta, 0 filas
                                   "Invalid Escape Character"
  x' OR Email != 'zzz              EJECUTA, devuelve 2 filas     ejecuta, devuelve 0 filas
  x' OR Id != null OR Email = '    EJECUTA, devuelve 2 filas     ejecuta, devuelve 0 filas

  (referencia: la org contenia 4 Contacts en total durante la prueba)

  LECTURA DE LOS DOS ULTIMOS CASOS, que son los importantes. Sin escape, ambas inyecciones NO
  fallan: ejecutan y devuelven 2 filas para un email que no existe. Como la logica clasifica por
  cantidad de filas, ese resultado habria producido `ambiguous` en lugar de `not_found`. O sea
  un valor controlado por el respondente podia alterar el estado de match de su propia respuesta.
  Con escape las mismas entradas devuelven 0 filas: el literal queda inerte y el estado es el
  correcto, not_found.

  Las dos ramas del replace son necesarias: la de comilla simple y tambien la de backslash, que
  sin escapar produce "Invalid Escape Character".

  Hay ademas una barrera previa ya verificada en la pasada anterior: el esquema zod del ingest
  rechaza con HTTP 400 los emails mal formados antes de persistir nada.


6. EDGE CASE — EL ESTADO `error`, QUE NO ESTABA DOCUMENTADO
============================================================
Se produjo de verdad, apagando el adaptador de namespace para que la consulta saliera con el
campo literal contra una org que no lo tiene — es decir, el escenario real de una org de ventas
mal configurada:

    veevartSalesContactId   = null
    veevartSalesMatchStatus = "error"
    engagementLevel         = null
    enrichedAt              = fechado
    excepcion relanzada     : Salesforce query failed (400): [{"message": ...

  El relanzamiento NO queda sin manejar. En server/src/routes/responses.ts:302-304 la llamada es
      void enrichResponseById(inserted.id).catch((e) => {
        console.error(formatBackgroundFailure("respondent-enrichment", inserted.id, e));
      });
  Se verifico expresamente porque un re-throw dentro de un fire-and-forget habria sido un
  defecto serio (unhandled rejection). No lo es: esta capturado.

  Lo que ese call site registraria en el log, con el error real de esta corrida:

      [respondent-enrichment] response 101 failed (Error)

      contiene el email del respondente?          NO
      contiene el nombre del campo o el SOQL?     NO

  Y como se ve en pantalla. contactMatchLabel (ResponsesDashboard.tsx:78-84) ejercitada:

      matched      -> "Matched"
      not_found    -> "Not found"
      ambiguous    -> "Multiple contacts found"
      error        -> "Lookup failed"
      not_checked  -> "Not checked"
      null         -> "Not checked"
      undefined    -> "Not checked"

      etiquetas distintas: 5
      "error" se distingue de "not_checked": SI

  Esto RESUELVE la duda que QA habia dejado abierta en la pasada anterior ("si ambos caen en el
  mismo fallback neutro, un administrador no puede diferenciar todavia-no-se-verifico de
  se-intento-y-fallo"). No caen en el mismo fallback: "Lookup failed" vs "Not checked". El
  colapso de null y undefined en "Not checked" es correcto: son las respuestas historicas.


7. OBSERVACION O4 — LOS DOS REQUISITOS ESTAN EN TENSION (no es defecto)
========================================================================
El AC pide que los datos de perfil nunca lleguen a logs publicos, y el PR 75 lo cumple bien:
formatBackgroundFailure reduce todo a operacion, id interno y una categoria de error de una
lista blanca. Verificado arriba: el email no aparece.

El efecto colateral es que el log tampoco dice QUE fallo. Ante una org mal configurada, lo unico
que queda escrito es "failed (Error)". Un operador no puede distinguir desde el log un
INVALID_FIELD por esquema, una caida de red o unas credenciales vencidas. Sumado a que el
enriquecimiento es fire-and-forget y la respuesta del usuario se guarda igual, la falla es
silenciosa en produccion: nadie se entera.

  No se levanta como defecto: ocultar el detalle es exactamente lo que el AC pide, y el PR
  eligio bien al priorizar la privacidad.

  SUGERENCIA, barata porque el dato YA se persiste: el estado queda guardado en
  veevartSalesMatchStatus = "error" en cada respuesta afectada. Basta con exponer un conteo de
  respuestas en estado `error` (por ejemplo en la pantalla de diagnosticos o en el dashboard)
  para que la falla deje de ser invisible, sin agregar ni un dato personal al log.

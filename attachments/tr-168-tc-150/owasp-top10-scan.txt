TR-168 · TC-150 (IM-868) · OWASP Top 10 (2021) — full applicability scan

## Contexto

PR #34 es un fix de lógica de cálculo de KPIs (`credit_card_transactions_income` capeado por POS Purchase Total). No introduce nuevos endpoints, no cambia auth surface, no cambia dependencias, no cambia infraestructura, no cambia storage. La única superficie ampliada es un campo adicional que el extractor lee del source SF org (`Auctifera__POS_Purchase__r.Auctifera__Total__c`).

Pero el DEFECTO OBSERVADO en TR-168 (execution SUCCEEDED con 1/3 orgs sin publicar) sí tiene implicaciones OWASP en las categorías de Integrity, Design y Logging.

## Detalle

### A01 · Broken Access Control — N/A
- El fix opera dentro de la boundary del servicio; no cambia perfiles, roles, ni ACL.

### A02 · Cryptographic Failures — N/A
- No cambia manejo de secretos, crypto, ni transporte.

### A03 · Injection — Applicable, PASS
- El SOQL query en `extract-raw-source-rows.queries.ts` construye la consulta usando params + escape SOQL estándar de jsforce.
- Diff review: la nueva columna `Auctifera__POS_Purchase__r.Auctifera__Total__c` es una string constante en la SELECT clause, no user input.
- Verdict: PASS.

### A04 · Insecure Design — Applicable, **FAIL**
- El diseño del orquestador Step Functions permite que la ejecución alcance estado terminal `SUCCEEDED` cuando 1 o más items del payload de subscriberOrgIds NO completaron su ciclo extract→compute→publish.
- Un contract robusto debería: (a) FAILAR la ejecución si algún item no completa, o (b) emitir estado `PARTIAL_SUCCESS` con detalle por item, o (c) al menos emitir logs / metrics explícitos por item skipeado.
- Evidencia: manual-20260821T155847-05f2c198 completó en 1min 13s con SUCCEEDED, pero LondonMarketing_Metrics__c record no fue upserted (LastModifiedDate no cambió). Ver TR-168 scenario 1.
- Severity: Medium (compromete integridad operacional, no expone datos).
- Verdict: **FAIL**. NO se crea issue separada; el fix debe abordarse cuando se corrija el defecto raíz de IM-868.

### A05 · Security Misconfiguration — N/A
- No cambia config de infra.

### A06 · Vulnerable & Outdated Components — N/A
- El diff no toca package.json. No dependencias nuevas.

### A07 · Identification & Auth Failures — N/A
- No cambia flujo de auth. `x-api-key` sigue siendo el gate.

### A08 · Software & Data Integrity Failures — Applicable, **FAIL**
- Definición: falla en garantizar que los datos publicados reflejen fielmente los datos procesados.
- Observado: el pipeline reportó SUCCEEDED con integridad de datos incompleta (London Marketing_Metrics__c NO se actualizó pese a estar en el payload).
- Un consumidor downstream (dashboard, executive, alert system) que confíe en el status SUCCEEDED verá el estado incorrecto para London y no sabrá que la data para esa org está stale/wrong.
- Severity: Medium.
- Verdict: **FAIL**.

### A09 · Security Logging & Monitoring Failures — Applicable, **FAIL**
- Definición: falta de logging que permita detectar events anómalos.
- Observado: no hay evidencia en el output del Step Functions (según lo que se puede inferir de que reportó SUCCEEDED) de que London se haya skipeado o hubiera un caught/retry.
- Un CloudWatch alarm sobre "orgs procesados vs orgs en payload" habría detectado la anomalía inmediatamente.
- Severity: Medium.
- Verdict: **FAIL**.

### A10 · Server-Side Request Forgery — N/A
- El servicio no hace requests basados en user input.

## Summary

- 4 Applicable · 1 PASS · 3 FAIL · 6 N/A
- Los 3 FAILs (A04, A08, A09) son manifestaciones del mismo defecto raíz (partial publish con SUCCEEDED status). NO se raise como defectos separados.
- Se cierran cuando el defecto de London se resuelva junto con el hardening del orquestador (failure mode explícito por item del payload).

## Diagnóstico definitivo

### H2 (race condition / parallel Map bug) — REFUTADA

- La misma slot (3ra posición del Map) que en el run fallido con London ahora procesa Vizcaya
  sin errores.
- El scheduler + dispatcher + Map iteration + Extract → Compute → Publish funcionan
  correctamente para arbitrary orgs.
- El "Caught error" del run fallido NO se manifestó — no es un patrón sistémico.

### H1 (defecto deterministico org-específico de London) — CONFIRMADA

- La Lambda ExtractSubscriberRawSourceRows falló DETERMINISTICAMENTE para
  subscriberOrgId=00DHr000001s53CMAQ en el run anterior.
- El error catcheado NO se reproduce cuando ese org se retira del payload.
- El defecto NO está en el orquestador; está localizado en la ejecución de Extract para el
  SF org de London Children's Museum.

### Categorías candidatas del defecto London-específico

1. **Auth broker fail** para el SF org de London (credentials expiradas, token roto, secret
   ausente en Secrets Manager, o VEEVART_HUB_SECRET_ARN mal-configurado para London).
2. **SOQL fail** — un query en la Lambda ExtractSubscriberRawSourceRows devuelve error sobre
   la shape de datos específica de London (campo custom faltante en su schema, picklist value
   inválido, referencia rota, o schema drift).
3. **Timeout parcial / partial extract fail** — un batch o page-through de SOQL falla a mitad
   de camino, causando el error interno de la Lambda.
4. **Permission issue** — el integration user en el AuthBroker no tiene los permisos
   necesarios en el SF org de London.

## Recomendación al dev

1. **Ir directo a CloudWatch Logs** de la Lambda ExtractSubscriberRawSourceRows invocation con
   `subscriberOrgId=00DHr000001s53CMAQ` timestamp `~2026-08-21T15:59:00Z` (link en la columna
   "Logs" de la row "Caught error" del Table view del run manual-20260821T155847-05f2c198).
   Ese log tiene el error real de la Lambda.

2. **NO enfocarse en el orquestador** — el hardening del Catch handler (WorkflowFailed si algún
   batch falla) sigue siendo válido para prevenir false-positive SUCCEEDED en el futuro, pero
   el defecto raíz es en Extract para London, no en el state machine.

3. **Bonus concern** sigue en pie: los publishFailureCount=25 (Textile) y 36 (DAC) del run
   anterior — items ocultos que fallaron dentro del publish exitoso. En este swap run también
   probable (no verificado — no capturé publishFailureCount).

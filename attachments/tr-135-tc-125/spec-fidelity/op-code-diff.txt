    * feat(IM-1084): automate IC 3.33 Membership Fields auto-populate (deactivate NPSP Last-Membership rollups)
    
    Rework 3.33 from a v1 that hand-listed 7 (wrong-org) rollup DeveloperNames
    behind a MANUAL "deactivate in the CRLP UI" handoff plus a SOQL verify that
    passed VACUOUSLY on the (mis-recorded) zero-rollup org, into a v2 HYBRID whose
    mutation is automated and whose verify is meaningful.
    
    Key finding (live on CamiloDevOrg): npsp__Rollup__mdt.npsp__Active__c is
    subscriber-writable via the synchronous CRUD Metadata API despite its
    DeveloperControlled field manageability — the NPSP default rollups are created
    in the subscriber org (NamespacePrefix null, bare Type.Dev fullName), so
    metadata.update('CustomMetadata', ...) commits (false<->true flip proven).
    
    T3 customMetadata op: add recordPattern mode — apply values to the
    DeveloperName-CONTAINS subset (SOQL LIKE), update-only, per-record read-back
    verify, TOLERATE-ABSENT (zero matches = informational success no-op, not a
    failure like allRecords). Threads the pattern through queryCmdtRecord; the
    pattern is escaped into the LIKE literal (not an identifier).
    
    3.33 v2 (case+template version 2, lockstep):
    - step 1 T3 customMetadata recordPattern 'LastMembership' -> npsp__Active__c=false
      (dynamic resolution, tolerate-absent, self-verifying)
    - step 2 T6 enable vnfp__Contact_Account_Fields_Auto_Population__c (unchanged)
    - step 3 MANUAL schedule the vnfp Contact/Account fill batches (guide format,
      one-line description)
    
    Live proof: with all 8 LastMembership rollups pre-activated on CamiloDevOrg,
    the real adapter deactivated all 8 and read-back verified each (success=true) —
    no longer a no-op. Tests: recordPattern subset + tolerate-absent zero-match
    adapter cases, 3.33 lockstep/surface spec. jest 1925 pass, tsc + eslint clean.
    
    * fix(IM-1084): escape SOQL LIKE wildcards in T3 customMetadata recordPattern
    
    Reviewer LOW: recordPattern built LIKE '%<pattern>%' with % and _ live, so a
    future author's pattern containing an underscore (SF DeveloperNames routinely
    have them, e.g. "Foo_Bar") would silently get _ as a single-char wildcard and
    over-match. After the existing quote/backslash escaping, escape % -> \% and
    _ -> \_ (SOQL's default LIKE escape char is \), run after escapeSoqlLiteral so
    the added backslash is not re-doubled; only the two op-supplied wrapper % stay
    wild. The shipped "LastMembership" pattern has no wildcards, so live behavior is
    unchanged (case+template stay v2 — op-robustness fix, not a spec change).
    
    - Doc comments (metadata-mutation-spec recordPattern field) now state the
      pattern is a plain substring whose %/_ are matched literally.
    - Test fake's SOQL mock upgraded to a faithful LIKE evaluator (\ escapes next
      char to literal, % = any run, _ = any single char).
    - New adapter test proves "Foo_Bar" matches NPSP_Foo_Bar literally, never
      NPSP_FooXBar. jest 1926 pass, tsc + eslint clean.

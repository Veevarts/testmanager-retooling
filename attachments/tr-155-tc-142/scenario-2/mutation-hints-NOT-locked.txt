===============================================================================
LO QUE NO SE CUMPLE  ->  la guarda de regresión es DECORATIVA
===============================================================================
Suite ejecutada en cada mutación:
  npx jest --runInBand membership-transactions-query.spec.ts   (33 tests)

  mutación                                                     resultado
  -----------------------------------------------------------  --------------------
  M1  borrar `OPTION (LOOP JOIN, MAX_GRANT_PERCENT = 5)`        33/33 PASA  <-- ❌
  M2  `MAX_GRANT_PERCENT = 5` -> `= 25`                         33/33 PASA  <-- ❌
  M3  borrar un `DROP TABLE IF EXISTS #MembershipLineItems`     33/33 PASA  <-- ❌
  M4  borrar `CREATE NONCLUSTERED INDEX IX_RecurringInstallments` 33/33 PASA <-- ❌
  M5  borrar `CREATE NONCLUSTERED INDEX IX_RefundedSalesOrders` 1 falla     (incidental)
  control (archivo restaurado)                                  33/33 PASA

Nota sobre M5: SÍ falla, pero no porque exista una aserción que proteja el índice.
Falla porque el helper `readStage` usa la línea `CREATE NONCLUSTERED INDEX IX_<name>`
como DELIMITADOR de parseo; al quitarla, el helper lanza
"staged statement #<name> has no index statement". Es rotura del parser, no una guarda.
Se comprueba en que M4 —un índice que ningún test lee— no rompe nada.

===============================================================================
POR QUÉ IMPORTA
===============================================================================
Los dos hints NO son una optimización marginal: SON el arreglo. La propia tabla de
mediciones del PR lo demuestra —

  | LOOP JOIN solo                        | err 8645              |
  | MAX_GRANT_PERCENT = 15 solo           | err 8645              |
  | LOOP JOIN + MAX_GRANT_PERCENT = 5     | 164.465 filas, 445 s  |

Sin la combinación, la query vuelve a fallar con error 8645 — es decir, vuelve a
devolver CERO FILAS PARA TODOS LOS CLIENTES, que es el bug original de este ticket.

Hoy nada impide que un refactor futuro borre esa línea: la suite sigue verde.
Lo mismo aplica al bloque `DROP` inicial, que el propio PR describe como
"load-bearing, not redundant" porque las conexiones del pool sobreviven a la query.

VEREDICTO DEL ESCENARIO: FAIL — no por el código, que es correcto, sino porque la
protección de regresión sobre el elemento más frágil del arreglo no existe.

ARREGLO SUGERIDO (barato)

En `membership-transactions-query.spec.ts`, añadir:

  it('keeps the memory-grant hints on the final assembly', () => {
    expect(query).toContain('OPTION (LOOP JOIN, MAX_GRANT_PERCENT = 5)');
  });

  it('keeps the leading drop block so a pooled session is re-runnable', () => {
    const firstInto = query.indexOf('\nINTO #');
    const lead = query.slice(0, firstInto).match(/DROP TABLE IF EXISTS #/g) ?? [];
    expect(lead).toHaveLength(15);
  });

  it('indexes every staged temp table', () => {
    const into = query.match(/\nINTO (#\w+)\n/g) ?? [];
    const idx  = query.match(/CREATE NONCLUSTERED INDEX IX_\w+ /g) ?? [];
    expect(idx).toHaveLength(into.length);
  });

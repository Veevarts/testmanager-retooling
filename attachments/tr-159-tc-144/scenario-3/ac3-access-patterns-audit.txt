AC3 — Every runtime application view has a documented DynamoDB query path and does not rely on broad Scan for normal traffic
Executed 2026-08-14 vs main HEAD.

============================================================================
VERDICT: FAIL (High severity)
============================================================================

The CDK data model defines 12 GSIs across the 4 non-settings tables — every
required access pattern has a documented Query path. BUT the runtime store
(`server/src/data/dynamodbStore.ts`) IGNORES those GSIs and uses ScanCommand
with client-side FilterExpression for almost all reads, including the FIVE
PUBLIC WIDGET ENDPOINTS. That is a broad-scan runtime, on request path, which
is what the AC prohibits.

============================================================================
Cost + latency + scaling impact
============================================================================

Every public request that reaches DynamoDB executes a full-table Scan with
FilterExpression:

  · Scan reads EVERY item and returns 1 MB of items per page (paginated in
    the store wrapper), then applies FilterExpression client-side.
  · Filter after read means DynamoDB bills for scanned items, not returned.
  · Cost grows LINEARLY with each table's total item count (surveys,
    responses, events). Today: cheap. At 100K surveys / 10M responses: painful.
  · Latency similarly grows.
  · Throttling: no hot partition today because the tables are small; will
    hit BURST throughput limits earlier than a Query-based design.

Every write to the responses table ALSO pays for 4 GSI writes (the 4 GSIs
are defined in CDK; DynamoDB writes fan out to each). So writes cost 5x
base — an amortized cost that only pays off if reads USE those GSIs.

Result: today we pay 5x the write cost for GSIs the code never queries.

============================================================================
Objective-fit
============================================================================

Ticket AC3, verbatim:
> Given the data model is reviewed, when access patterns are compared against
> the table/index design, then each supported application view has a documented
> DynamoDB query path without relying on broad scans for normal runtime behavior.

Pre-fix reproduces the reported design: CDK defines GSIs correctly.
Post-fix (actual runtime): Uses Scan for those views instead of Query.
Does it meet the objective? NO. The AC is not satisfied.

============================================================================
Recommendation
============================================================================

Rewrite the read methods on `DynamoSurveyStore` to use QueryCommand on the
existing GSIs. The GSI keys are already computed in the item shape helpers
(surveyItem, responseItem, etc.); the query path is a one-line swap of
`this.scan(...)` for `this.query({ TableName, IndexName, KeyConditionExpression })`.

Priority order by public-path impact:
  1. listActiveGeneralSurveys → Query GSI1 (surveys) — HOT PATH, every after-login
  2. listSurveysByFeatureId  → Query GSI2 (surveys) — HOT PATH, every /features/:id/surveys
  3. countEvents (respondent scope) → Query base PK (respondent-state) — HOT PATH
  4. countEvents (survey+day scope) → Query GSI1 (respondent-state) — HOT PATH
  5. getFeatureBySlug → Query GSI1 (surveys) — HOT PATH, every /survey/:slug
  6. listResponses (admin filters) → Query GSI1/2/3/4 as filters allow — Dashboard/CSV path
  7. getOrganizationBySalesforceOrgId → Query GSI2 (organizations)
  8. listOrganizations, listFeatures → OK as Scan if they're admin-only-once loads

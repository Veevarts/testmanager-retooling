Code review: DynamoSurveyStore.importSnapshot() (line 449 in dynamodbStore.ts)
------------------------------------------------------------------------------

For each section, PUTs items into the correct table with the correct PK/SK
+ GSI keys. Preserves the source `id` (numeric) as the sort/partition key
identifier. After all writes, updates 6 counters via `setCounter(name, maxId)`:

  private async setCounter(name: string, nextId: number): Promise<void> {
    if (nextId <= 0) return;
    const existing = await this.get<{nextId?: number}>(this.tables.settings,
      { PK: `COUNTER#${name}`, SK: "META" });
    if (typeof existing?.nextId === "number" && existing.nextId >= nextId) return;
    // else PUT the new counter
  }

Key behavior:
  · **ID preservation**: PUTs at deterministic PK (`SUBJECT#<id>`, `SURVEY#<id>`,
    etc.), so re-running the import overwrites the same items (upsert semantics).
  · **Counter idempotency**: `setCounter` never LOWERS a counter — if the
    stored value is greater than or equal to the max imported id, it leaves
    the counter alone. Prevents ID collisions when import is re-run against
    an already-partially-migrated table.
  · **No transactional guarantees across tables**: if the process dies
    mid-import, the target table has partial data, but re-running is safe
    (idempotent per above).

Validation mechanism — what the AC asks vs what the importer does
------------------------------------------------------------------------------

AC6 requires the migration to be validated by:
  1. Record counts
  2. Key relationships
  3. Representative survey samples
  4. Response export checks

Importer's built-in validation:
  1. ✓ Record counts — LOGGED (`{section: count}` printed after import)
  2. ✗ Key relationships — NOT ENFORCED (no check that `responses[i].surveyId`
     resolves to an existing survey in `surveys[]`)
  3. ✗ Representative sample — NOT ENFORCED (importer doesn't sample or
     round-trip check any items)
  4. ✗ Response export parity — NOT ENFORCED (no PRE/POST CSV checksum)

None of items 2-4 have automated tooling in the repo. To satisfy the AC
fully, someone would need to write an external validation script that:
  · Re-reads the target tables after import
  · Cross-checks (responses.surveyId ⊆ surveys.id) and similar
  · Samples N random items and re-fetches them
  · Exports the response CSV PRE (via the source SQLite) and POST (via
    DynamoDB) and compares checksums

2. POR QUE ESTE ARREGLO NO ERA COSMETICO
=========================================
En la primera pasada QA lo reporto como "dos fechas distintas en la misma sesion". Al ejercitar
ahora la funcionalidad se ve que el impacto era mayor: el parametro `today` NO es decorativo,
alimenta los contadores por dia del reporte de elegibilidad.

Demostracion sobre el entorno desplegado, con el MISMO respondente y el MISMO instante,
variando unicamente el criterio de fecha:

  Instante simulado: 2026-09-16T02:30:00Z  =  21:30 hora local en UTC-5
    criterio UTC ingenuo (el bug viejo) -> 2026-09-16
    criterio local correcto (el actual) -> 2026-09-15

  Respondente con 1 impresion registrada hoy sobre la survey 17 (maxShowsPerDay = 1):

    today=2026-09-15 (LOCAL, correcto)
      eligible             : false
      reason               : max_shows_per_day_reached
      todayImpressionCount : 1
      surveysShownToday    : 1

    today=2026-09-16 (UTC, el bug viejo)
      eligible             : true
      reason               : null
      todayImpressionCount : 0
      surveysShownToday    : 0

  Con el bug, la pantalla de diagnostico habria respondido "es elegible, nada la bloquea"
  cuando en realidad el tope diario SI la estaba bloqueando. Es decir, la herramienta cuya
  unica funcion es explicar por que una encuesta no se entrega habria dado la respuesta
  CONTRARIA durante las ultimas cinco horas de cada dia.

  Eso eleva el hallazgo de "inconsistencia visual" a "diagnostico incorrecto en su funcion
  principal", y confirma que valia la pena arreglarlo antes de encender el flag.


3. LA FUNCIONALIDAD DE DIAGNOSTICO, EJERCITADA
===============================================
CORRECCION A LA PRIMERA PASADA. El 2026-09-11 este run afirmo que "la pagina de diagnosticos no
consume ningun endpoint propio". Esa descripcion era imprecisa: SI existe un endpoint dedicado,

    GET /api/admin/features/:featureId/respondent-state/:respondentId

que es el que DiagnosticsPage invoca via api.features.respondentState(...). Las conclusiones de
seguridad de aquella pasada NO cambian, y se re-verificaron aqui:

    - el endpoint ya existia ANTES del PR 71
        git show 4458647c~1:server/src/routes/features.ts | grep -c respondent-state  -> 2
        git show 4458647c:server/src/routes/features.ts   | grep -c respondent-state  -> 2
      o sea el PR 71 no agrego superficie de API nueva, que era la afirmacion importante.
    - vive bajo /api/admin, detras de requireAdminAuth (app.use("/api/admin", requireAdminAuth)).
    - no hay ningun router de diagnosticos montado aparte.

CONSECUENCIA UTIL: como el flag solo gatea la RUTA DEL CLIENTE, la logica de diagnostico si es
ejercitable con sesion de administrador. Ya no hace falta encender el flag para validar que la
funcionalidad hace lo que el ticket promete.

Ciclo ejecutado sobre el entorno desplegado, subject "QA TC-161 Gates" (featureId 11),
survey 17 con maxShowsPerDay = 1, respondente nuevo:

  Paso                        eligible  reason                      impressionCount  todayCount
  --------------------------  --------  --------------------------  ---------------  ----------
  respondente sin actividad     true    null                              0              0
  se registra 1 impresion       false   max_shows_per_day_reached         1              1

  El reporte tambien devuelve el bloque global:
      maxSurveysPerDay 10, surveysShownToday 0 -> 1, limitReached false

  Y por cada encuesta candidata informa: active, audience, appliesToRequestedFeature,
  allowsClientOrg, los limites configurados (maxDismissals, maxShowsPerDay, cooldownDays) y los
  contadores (impressionCount, todayImpressionCount, dismissalCount, dismissalCountAllTime,
  responseCount, respondentResponseCount, lastRespondedAt).

  Es exactamente lo que el README describe como la feature: "read-only eligibility diagnostics
  for a subject, respondent, organization, user creation date, and usage count to see the exact
  reason a survey is eligible or blocked".

LIMITE DECLARADO: lo verificado es la FUNCIONALIDAD (el reporte de elegibilidad y su manejo de
fechas) a traves de su propia API. El RENDER de la pagina sigue sin ejercitarse porque el flag
continua apagado, y encenderlo exige un rebuild del cliente. No se declara probado el render.
Se deja constancia de que eso NO es una omision del ticket: entregar la pantalla apagada es
precisamente lo que IM-1253 pide.

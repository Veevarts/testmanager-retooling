Technical + Security regression plan — PR Veevarts/MigrationToolETL#145
========================================================================

Change surface: 3 files in the SQL-server shop extractor:
  - queries/shop/item_variant.sql          (-21 / +12 lines — removes WHERE ISACTIVE=1 filter, adds Bypass_Stock CASE, drops dead history join)
  - queries/shop/catalog_item.sql          (-1 / +34 lines — adds Bypass_Stock CASE with EXISTS-based derivation)
  - query-regression/shop-item-variant-coverage-query.spec.ts (NEW — 87 lines, 7 static contract assertions)

Runtime: SQL text executed by the MigrationTool ETL pipeline against a customer's
restored Altru backup (SQL Server). Output CSVs are consumed by the Salesforce
bulk-upsert loader (`sf data upsert bulk --sobject Auctifera__Item_Variant__c` /
`Auctifera__CatalogItem__c` / `Auctifera__Sale_Item__c`), keyed by
`Implementation_External_ID__c`. No Apex / no Node runtime path changes.

Blast radius
------------
- Every future Altru shop migration inherits the new extraction cardinality
  (variants: all rows instead of ISACTIVE=1 only) and the new Bypass_Stock
  semantics (variant-level + catalog-level).
- MigrationTool ETL callers: no consumer breaks — the queries return more columns'
  values but no new column names (Bypass_Stock__c already existed as literal 0).
- Salesforce side: `Auctifera__Bypass_Stock__c` field must exist on both
  Item_Variant__c and CatalogItem__c (confirmed by SOQL on illinois-trainings —
  field present).
- Related IM-809: the sibling `shop-discount-query.spec.ts` pattern is preserved;
  this PR follows it verbatim.

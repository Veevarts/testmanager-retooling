AC3 — sin fan-out y sin pérdida
==================================================================================================
  El conteo de filas es IDÉNTICO entre BASE y POST en las dos fuentes. Ese es el riesgo real de
  agregar un join a una tabla sin constraint único (`PRODUCTVENDOR` no lo tiene sobre `PRODUCTID`),
  y el `OUTER APPLY ... TOP 1` lo evita por construcción. Medido, no razonado.

⚠️ LÍMITE DE LO QUE ESTOS DATOS PUEDEN PROBAR — hay que declararlo
==================================================================================================
  Se midió explícitamente la forma de los datos en AMBAS fuentes:

      productos con MÁS de una fila en PRODUCTVENDOR ....... 0   (illinois_2)   0 (tucson)
      filas cuyo vendor es una PERSONA (ISORGANIZATION=0) .. 0   (illinois_2)   0 (tucson)
      productos SIN ninguna fila en PRODUCTVENDOR .......... 0   (illinois_2)   0 (tucson)
      productos sin vendor-organización que califique ...... 0   (illinois_2)   0 (tucson)

  Consecuencias honestas:
  1. Como NINGÚN producto tiene más de una fila de vendor, el **desempate** (`TOP 1` + `ORDER BY`)
     NO se ejercita con datos reales. Es consistente con lo que el propio PR dice
     ("real data is currently 1:1"), pero significa que el determinismo NO está probado en vivo.
  2. Como NINGÚN vendor es persona, el **guard `ISORGANIZATION = 1`** tampoco se ejercita: no hay
     ninguna fila que el guard tenga que descartar.
  3. Como NINGÚN producto carece de fila de vendor, estos datos **no distinguen `OUTER APPLY` de un
     `INNER JOIN`**: con cobertura 100% los dos darían el mismo conteo. La garantía de no-pérdida
     está probada estructuralmente (el `OUTER`) pero no discriminada por los datos.

  Los tres puntos quedan para el fixture de testcontainers (escenario 3), que es el único lugar
  donde se pueden sembrar esos casos. Se declara; no se finge.

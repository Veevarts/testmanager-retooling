TR-149 / TC-110 · Escenario 3 — AC4: desempate determinista, guard ISORGANIZATION y fallback
Fecha: 2026-07-31

POR QUÉ ESTE ESCENARIO NO SE PUEDE PROBAR CON DATOS REALES
==================================================================================================
Se midió la forma de los datos en las DOS fuentes Altru disponibles (escenario 1):

                                                  illinois_2   tucson
    productos con MÁS de una fila en PRODUCTVENDOR ....  0        0
    filas cuyo vendor es una PERSONA .................   0        0
    productos SIN ninguna fila de vendor .............   0        0

Con esa forma de datos:
  · el desempate (`TOP 1` + `ORDER BY`) nunca se ejercita — no hay empate que romper;
  · el guard `ISORGANIZATION = 1` nunca descarta nada — no hay vendor persona;
  · el `OUTER` no se distingue de un `INNER` — no hay producto sin vendor.

Es coherente con lo que el propio PR admite ("real data is currently 1:1"). Por eso el ÚNICO lugar
donde este AC es demostrable es el fixture de testcontainers, que siembra los casos a mano.

EL FIXTURE SIEMBRA EXACTAMENTE EL CASO DIFÍCIL
==================================================================================================
`shop-discount-query-fixture.ts` (el fixture de IM-1107, extendido por este PR) agrega la tabla
PRODUCTVENDOR y DOS filas para EL MISMO producto:

    ID    ...081   VENDORID = SHOP_VENDOR_ORG_ID    (CONSTITUENT con ISORGANIZATION = 1)
                   DATEADDED = DATECHANGED = 2025-01-01      <- la MÁS VIEJA
    ID    ...082   VENDORID = SHOP_CONSTITUENT_ID   (CONSTITUENT con ISORGANIZATION = 0, persona)
                   DATEADDED = DATECHANGED = 2025-02-01      <- la MÁS NUEVA

Y en CONSTITUENT: ('SHOP_CONSTITUENT_ID', 0, ...) y ('SHOP_VENDOR_ORG_ID', 1, ...), o sea el flag
ISORGANIZATION en 0 y 1 respectivamente.

Esta construcción es la que discrimina de verdad. Si el guard estuviera aplicado como POST-FILTRO
(o faltara), el `TOP 1` elegiría primero la fila de la PERSONA por ser la más reciente y luego la
descartaría -> el resultado sería NULL, o peor, el id de la persona. Al estar el JOIN a CONSTITUENT
DENTRO de la subconsulta correlacionada, la persona nunca entra al conjunto candidato y el `TOP 1`
cae al vendor-organización más viejo.

LO QUE SIGUE SIN PROBARSE, Y SE DECLARA
==================================================================================================
El fixture prueba el guard y el fallback. NO prueba el DESEMPATE PURO: no hay ningún caso sembrado
con dos filas de vendor que sean AMBAS de organización y compitan por fecha, ni un empate exacto de
`DATECHANGED`/`DATEADDED` que obligue a usar el tercer nivel del ORDER BY (`pv.ID`).
Ese tercer nivel es lo que hace la elección reproducible cuando las fechas empatan, y hoy sólo está
verificado a nivel de texto (el spec exige que el ORDER BY esté escrito así), no de comportamiento.
Riesgo real: BAJO — con fechas distintas el orden ya es determinista; el empate exacto es un caso
de borde. Recomendación para el repo: sembrar dos vendors-organización con la misma fecha y assertar
cuál gana.

VEREDICTO ESCENARIO 3: PASS — el guard y el fallback quedan probados con comportamiento real contra
SQL Server. El desempate por `pv.ID` en caso de empate exacto queda cubierto sólo por contrato.

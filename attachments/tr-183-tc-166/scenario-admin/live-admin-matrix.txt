--- A4: por que el Start Date es realmente LOCAL y no UTC ------------------------------

La observacion de A3 por si sola NO distingue local de UTC, porque al momento de medir
(16:27 hora local, 21:27 UTC) ambas zonas caen el mismo dia. Para no dar un PASS de
conveniencia se verifico el helper del codigo:

    export function localTodayDateInputValue(now = new Date()): string {
      const localTime = now.getTime() - now.getTimezoneOffset() * 60_000;
      return new Date(localTime).toISOString().slice(0, 10);
    }

Compensa el offset ANTES de serializar, que es la tecnica correcta. Ejecutado contra cuatro
instantes, dos de ellos en el borde donde una implementacion ingenua se equivocaria:

  mediodia local                 local=2026-09-11  helper=2026-09-11  OK
  19:00 local (00:00Z del dia 12) local=2026-09-11  helper=2026-09-11  OK   (UTC ingenuo daria el 12)
  23:30 local (04:30Z del dia 12) local=2026-09-11  helper=2026-09-11  OK   (UTC ingenuo daria el 12)
  00:30 local del dia 12          local=2026-09-12  helper=2026-09-12  OK

El AC pide "the current local date" y eso es exactamente lo que entrega, incluso en las cinco
horas finales del dia local donde UTC ya avanzo. Contrasta de forma favorable con el filtro de
fechas del dashboard (observacion O1 de TR-177), que si evalua en UTC.

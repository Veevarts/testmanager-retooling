AC10 — las tres reglas configuradas a la vez
-----------------------------------------------------------------------------

  caso                                              entregada   contadores
  ------------------------------------------------  ----------  ------------------
  A  control limpio, usageCount=1 (todas cumplidas)  [2]  SÍ     imp 0 · dis 0
  B  solo TRIES incumplido (usageCount=2)            []   no     imp 0 · dis 0
  C  solo DISMISSALS incumplido                      []   no     imp 0 · dis 2
  D  solo IMPRESIONES incumplido                     []   no     imp 1 · dis 0
  E  LAS TRES incumplidas (usageCount=2)             []   no     imp 1 · dis 2

Cada regla bloquea por separado, la combinación bloquea, y el control positivo

VEREDICTO primera mitad de AC10: PASS.

VERIFICABILIDAD DE LA RAZÓN — PASS PARCIAL, con un matiz que conviene reportar.
El AC pide que "la razón se pueda verificar desde el estado registrado o la
diagnóstica". El endpoint GET /api/admin/features/:id/respondent-state/:respondentId
SÍ existe y devuelve por survey: limits{maxDismissals,maxShowsPerDay,cooldownDays},
counters{impressionCount,todayImpressionCount,dismissalCount,dismissalCountAllTime,
responseCount,lastRespondedAt}, eligible y reason.

  - Por CONTADORES la causa se distingue perfectamente: los casos C, D y E se
    diferencian entre sí (dis 2 / imp 1 / ambos).
  - Pero el campo `reason` devuelve "general_client_org_missing" en los cinco
    casos, incluido el control que SÍ se entrega. Es porque ese endpoint de admin
    no recibe contexto de organización, así que para una General acotada por
    organización nunca puede evaluar la audiencia y se corta antes de llegar a
    las reglas de frecuencia.

  O sea: la razón es verificable por contadores, NO por el campo `reason`, que
  para generales org-scoped es engañoso — dice "falta la org" cuando la survey
  es perfectamente entregable. Vale la pena que el endpoint acepte clientOrgId /
  salesforceOrgId como parámetros.

-----------------------------------------------------------------------------
PRECEDENCIA — nota de diseño
-----------------------------------------------------------------------------
El AC habla de "la regla más restrictiva no cumplida". El orden real en
lib/surveyRuntime.ts es SECUENCIAL FIJO y gana la PRIMERA incumplida:

  audience -> start_date -> triggerType -> start/end -> maxResponses ->
  onePerRespondent -> cooldown -> triesBetweenShows -> maxShowsPerDay -> maxDismissals

El resultado observable coincide con lo que el AC pide (cualquier regla incumplida
bloquea la entrega), pero CUÁL bloquea lo decide el orden del código, no una noción
de restrictividad. Se documenta para que producto confirme que es el comportamiento
esperado.
